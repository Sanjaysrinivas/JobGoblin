## Product Intent

JobGoblin is a private, self-hosted job-search workspace for one owner and a few invited users. It helps users discover jobs, organize opportunities, compare resumes to roles, draft grounded application materials, track applications, plan follow-ups, prepare outreach, and prepare for interviews.

Hard product boundaries:

- This is not an auto-apply product.
- The app must not silently send email, contact recruiters, submit forms, scrape LinkedIn, or perform external outreach.
- Every external action must stay explicit, user-reviewed, and user-triggered.
- AI may summarize, rephrase, rank, explain, and draft from user-provided facts, but must not invent employers, dates, degrees, certifications, skills, achievements, or work history.
- ATS-style scores are estimates and must be labelled as estimates.
- Multi-user data isolation is mandatory; user-owned records must be scoped by `user_id`.
- The default deployment model remains local/private, with optional private tunnel access.

## Architecture Decisions

### Hosting And Topology

Decision: run everything in one Docker Compose stack on the owner's machine.

Rationale:

- Keeps hosting cost at zero.
- Keeps private data local.
- Allows Ollama to run beside the app without external AI APIs.
- Fits the project's private/self-hosted product boundary.

Trade-off:

- The app is available only while the host machine is on.
- Operator docs and backup/restore matter more because the owner controls the runtime.

### Same-Origin Caddy Proxy

Decision: Caddy is the browser entry point. It routes `/` to the Next.js frontend and `/api/*` to FastAPI.

Rationale:

- Avoids CORS and cross-site cookie complexity.
- Lets auth use HTTP-only SameSite=Lax cookies cleanly.
- Keeps local and tunnel access behavior closer to production.

Implication:

- Integration tests and manual smoke should prefer `http://localhost:8080`, not direct frontend/backend ports.

### Authentication And Access Control

Decision: invite-only app with email/password, optional Google OAuth, TOTP MFA, and allowlist support.

Rationale:

- Product is private, not public SaaS.
- Owner can invite trusted users.
- Google OAuth is fail-closed unless configured and allowlisted.

Implementation rule:

- User-owned data must always be filtered by authenticated `user_id`.
- Cross-user access should return 404/401 without leaking object existence.
- Logs must not include secrets, resume text, tokens, or sensitive profile data.

### AI Provider Layer

Decision: all AI calls go through provider abstraction with `MockProvider` and `OllamaProvider`.

Rationale:

- Tests stay deterministic with mock AI.
- Runtime can use local Ollama without changing business logic.
- Future providers can be swapped behind the interface.

Current local baseline:

- `llama3.2:3b` is the proven local model.
- It is acceptable as the smoke baseline for parse/analysis/cover-letter flows.
- Prompt quality still needs manual review and tuning.

### Scoring Model

Decision: resume-to-job score is hybrid: deterministic matching for numeric scoring, AI for explanation and recommendations.

Rationale:

- Numeric scores remain explainable and stable.
- AI adds useful reasoning without becoming the sole source of truth.
- The UI can honestly label scores as estimates.

Rule:

- Do not present scores as guaranteed ATS outcomes.

### Resume Source Facts And Versions

Decision: uploaded resume source facts are preserved on `resumes`; editable/tailored variants live in `resume_versions`.

Rationale:

- Users need a trusted original source.
- Edits and tailoring should not accidentally overwrite uploaded facts.
- Downstream flows can use the current version while still preserving provenance.

Current limitation:

- PR #25 supports resume versions and current-version behavior, but downstream application linkage and explicit version selection in every workflow are not complete yet.

### Job Discovery Architecture

Decision: the local model does not directly browse the web. Job Discovery needs an explicit provider/search layer.

Target flow:

```text
User preferences + resume/profile facts
  -> query builder
  -> search/job provider API
  -> fetched raw results/pages
  -> normalized discovered job records
  -> dedupe
  -> local Ollama ranking/explanation
  -> user saves selected results into Jobs
  -> existing analysis/cover-letter/application workflow
```

Rationale:

- Ollama is a reasoning layer, not a web crawler.
- Provider abstraction lets the app start with one API and add more later.
- Search APIs or public ATS/company boards are safer than direct scraping of sites with restrictive terms.
- Keeping discovered results separate from saved jobs prevents clutter and allows review/dismiss/dedupe behavior.

Boundary:

- Discovery stops at finding, ranking, and saving candidate jobs. It must not auto-apply or silently contact anyone.

### Data Storage

Decision: PostgreSQL via SQLModel/Alembic for structured data; local mounted storage for uploaded files behind a storage interface.

Rationale:

- PostgreSQL is already in Compose and supports real relational workflows.
- Alembic keeps schema evolution reviewable.
- Storage interface leaves room for S3/R2/MinIO later without exposing raw paths.

### Frontend Shape

Decision: Next.js App Router frontend with feature-oriented components and typed lib helpers.

Rationale:

- Keeps browser workflows close to API resource boundaries.
- Caddy same-origin design means frontend calls `/api/*` through one origin.
- Local helpers in `frontend/lib` should mirror backend routes and response types.

## Next Implementation Plan: Job Discovery MVP

Build this from a fresh branch off `dev`.

### Slice 1: Preferences

Backend:

- Add `job_search_preferences` or extend profile with structured discovery preferences.
- Suggested fields:
  - target countries
  - target cities/regions
  - remote/hybrid/onsite preference
  - desired titles
  - seniority
  - industries
  - required/optional keywords
  - excluded keywords
  - visa sponsorship requirement
  - blocked companies
- Scope every row by `user_id`.

Frontend:

- Add settings/profile UI for job search preferences.
- Keep it editable and explicit; no hidden inferred preferences without user review.

### Slice 2: Discovery Data Model

Add tables similar to:

- `job_search_runs`
  - `user_id`
  - preferences snapshot
  - query terms
  - provider
  - status
  - timestamps
- `job_search_results`
  - `user_id`
  - run id
  - source/provider
  - source url
  - canonical url
  - title
  - company
  - location
  - work mode
  - description/snippet/raw text
  - posted date if available
  - dedupe key/hash
  - rank/match metadata
  - status: new, saved, dismissed, blocked

Keep discovered results separate from `jobs` until the user saves one.

### Slice 3: Provider Interface

Create a provider abstraction. Example shape:

```python
class JobSearchProvider(ABC):
    async def search(self, query: JobSearchQuery) -> list[RawJobSearchResult]: ...
```

Start with one provider. Practical options:

- Brave Search API
- SerpAPI
- Google Programmable Search
- Adzuna
- Jooble
- public Greenhouse/Lever/company board connectors later

Avoid direct LinkedIn/Indeed scraping as the first implementation. It is brittle and can violate terms.

### Slice 4: Query Builder

Use preferences plus selected resume/current resume version/profile facts to build search queries.

Examples:

- `Python FastAPI backend engineer remote Germany`
- `Platform engineer PostgreSQL Docker visa sponsorship Netherlands`
- `Backend developer Kubernetes AWS Canada`

The query builder can use Ollama, but it must keep output bounded and reviewable.

### Slice 5: Ranking And Save-To-Jobs

For each normalized result:

- Estimate preference fit.
- Estimate resume fit using current resume/profile facts.
- Explain why it is a match or not.
- Highlight location/visa/work-mode compatibility.
- Let the user save selected results into the existing `jobs` table.

Saving should copy the title, company, location, source URL, source, work mode, description, and source metadata into a normal job record.

### Slice 6: Discover Jobs UI

Add a dedicated page, likely `/discover` or `/jobs/discover`.

Expected controls:

- Preferences summary.
- Country/location filters.
- Search/run button.
- Provider/status indicator.
- Results list with ranking, reasons, source link, save/dismiss actions.
- Saved result state.
- Link into normal job detail/analysis after save.
